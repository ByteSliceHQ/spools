Record scopes: one Spool for a business whose groups (branches, regions, teams) must each see only their own records. Add `scopes` to `crm.config.json` (the scope field of each scoped object, and the roles a scope is held with) and say who holds what with `clerk({ scopes: 'organizations' })`, `devAuth({ scopes })` or `scopes` in `src/app/extensions.ts`. Every store is then behind a guard that narrows each read, count, change and delete to the scopes of whoever the request is for, so pages, search, reports, exports, imports, the tool API and extensions all keep to it. A Spool without `scopes` is unchanged. The scope tests run on PGlite, Postgres and Prisma.

With Clerk, a scope is the organization's id (`org_...`), never its slug, which an organization's administrators can rename. A role marked `all` counts only from the organizations named in `everyScopeFrom`, by id: without it nobody reaches every scope, and the server says so when it starts. Every membership and organization is read, a page at a time.

For everyone, with or without scopes: seven system tables (`activities`, `tasks`, `notes`, `favorites`, `record_folders`, `file_uploads`, `sequence_runs`) gain a nullable `scope` column. Run `bun run crm:gen` and `bun run db:push` (or plan and apply a migration). Nothing else changes until you add `scopes`.

Turning scopes on: give every record of a scoped object its scope, then run `spools scopes backfill` (add `"db:scopes": "spools scopes backfill"` to your scripts) so rows written before take their record's scope. Workflows that write back through the tool API must send the `grant` from their input as the `X-Spools-Grant` header: the starter's `new_contact` and `enrich_contact` now do, and `crm_event` in `swirls/schemas.swirls` lists `grant`; copy both changes into a Spool made before, and deploy the workflows. A grant is for the one record its workflow was started for (`get`, `update` and `add_note` answer about that record only; `search` and `create` are refused under it), is refused once the person who started the workflow is off the access list, reaches no more than that person holds when it is used (a scope they have lost is lost to their workflows too), and lasts 15 minutes unless `scopes.grantMinutes` says: set it longer for a workflow that waits before it writes back. Running an action, an automation's target or a sequence for a record needs the right to change that record, checked before anything starts. The assistant needs federation, and its record tools are refused in chat. See docs/security.md#record-scopes.

What the guard refuses besides: deleting a record while records of a scope the deleter can't change point at it (the database would clear their relation), a shared record included; deleting a record that others take their scope from, when a scope field is a relation (that relation is now `ON DELETE RESTRICT` in the schema: `bun run crm:gen` and push, if you have one); changing a record's id; and `*`, or a value a select scope field doesn't offer, as a record's scope. A scope the resolver doesn't list is refused when a record is saved. A refusal is its own failure, `ScopeRefused`, in every store method's failures beside `DatabaseError`: code that names the store's failures in a type adds it, and `catchTag('DatabaseError', ...)` no longer sees refusals. Sequence runs held for want of a scope are left out of each tick's batch, so they never keep later runs from being sent.

Someone who can't change what a page shows is given no controls for it: no adding, importing or deleting records, no editing in a cell, on a board or in a record's details, no record actions, tasks, notes, logged calls or emails, and no file changes. The server refuses each as before.

For a database adapter that writes its own `ORDER BY` (one built on `sqlBackend` needs nothing): `OrderBy` has a new form, `{ related: [relation, column], where }`, which the guard hands on in place of `[relation, column]` when the related object is scoped. A row whose related record doesn't meet `where` must sort as a row with none. See docs/database.md#record-scopes. The guard holds a record a new row points at, and a record being deleted while what points at it is counted, so a backend's `lock` must be a real row lock.

For a file store adapter of your own: the `FileStore` port has a new method, `fileFolder(id)`, which says which folder a file is in (`null` at the top level; a `FilesError` with `status: 404` when the file is gone). A Spool with scopes asks it about a file that a folder's listing, which stops at a limit, didn't reach.

Also new: `asSystem` in `@swirls/spools/extensions` for scripts, `@swirls/spools/scopes` (the types), the `spools scopes backfill` command, and `/api/files/<id>?folder=<folder id>`, which the file browser's links now carry. A folder listing says whether its reader can change it (`canWrite`, on the listing and on each folder), and `update`, `remove` and `lock` on the store refuse a call with no condition of the caller's own, whoever makes it.
